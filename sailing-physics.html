Sailing Physics Model

How wind becomes boat speed: a server-authoritative, polar-table-driven arcade sailing model built for touch controls and 10–20 Hz multiplayer sync.

01 · Scope

Overview

This is the first of three design docs for the sailing game — physics, networking, and touch controls — and it comes first because it's the one nothing else can be honestly designed without: the networking layer needs to know what state it's syncing, and the control scheme needs to know what it's actually steering.

The model here optimizes for four things, roughly in order: it has to feel responsive on a phone (no waiting for a "real" wind simulation to resolve), it has to be cheap enough to run for 20+ boats at once server-side, it has to be replayable and cheat-proof (every boat's speed is a deterministic function of server-known inputs, never something the client asserts), and it should reward reading the wind without requiring the player to understand true lift/drag sailing theory.

The approach: real sailing has a well-known, well-documented relationship between wind angle and achievable boat speed — the polar diagram. Instead of simulating sails as aerofoils, the server looks up a boat's target speed from a polar table indexed by wind angle and wind strength, then applies trim, turning, and tack-transition penalties on top. It's the same simplification most sailing games converge on, and it happens to map cleanly onto a lag-tolerant, cheat-resistant multiplayer architecture.

02 · Environment

Wind model

Everything in this doc keys off true wind angle (TWA): the angle between the wind's origin direction and the boat's heading, measured 0–180° regardless of port or starboard side. 0° is dead into the wind; 180° is dead downwind.

The wind itself is a single shared state per race, computed server-side from a per-race seed so every client sees identical conditions without the server having to broadcast every micro-fluctuation:

WindState — fields the server evaluates each tick
FieldTypePurpose
baseDirectionDegfloatslow-drifting mean direction, race-seeded
baseSpeedKnotsfloatslow-drifting mean strength, race-seeded
gustPhasefloatsine/Perlin offset layered on top for short gusts
directionDegfloatresolved value clients actually sail against
speedKnotsfloatresolved value clients actually sail against

Direction and speed both drift on independent, slow sine/noise curves seeded from raceSeed, so the function is pure: WindModel.Evaluate(raceSeed, serverTime) returns the same answer everywhere it's called. That determinism is what makes it safe to let clients run a cosmetic copy of the same function for smooth rendering between snapshots — but only the server's evaluation is ever used to resolve speed, position, or race results. A client that reports a different local wind reading is either lagging or lying, and either way the server's number wins.

Boat speed is a function of the wind relative to the boat, not compass-absolute wind, so every polar lookup below first reduces to TWA = |wrapAngle(windDirectionDeg − boatHeadingDeg)|.

03 · Core model

Points of sail & the polar model

A real boat can't sail directly into the wind — there's a cone, typically 35–45° either side of dead upwind, where sails simply luff and the boat stalls. Sailors call this the no-go zone, or being "in irons." Outside that cone, speed climbs as the angle opens up, typically peaking somewhere around a beam reach (90° TWA), then eases off again as the boat runs deeper downwind, because at some point the boat is limited by wind speed itself rather than sail efficiency.

Inside the cone, speed doesn't clamp to zero the moment you cross the 40° line — that reads as a wall, not a boat. It eases down smoothly as the angle tightens, crosses zero somewhere well short of dead upwind, and at true 0° TWA the boat is making slow sternway: drifting backward, stern-first, at a speed set by how hard the wind is blowing. That's what a stalled boat with luffing sails actually does, and it turns "in irons" from a hard failure state into a recoverable one — bear away and drive returns the same way it left.

For grounding: on a well-documented one-design polar, optimum upwind VMG lands around 45° TWA at roughly 7.4 kt boat speed (5.2 kt made good toward the mark), and optimum downwind VMG lands around 135° TWA at roughly 5.7 kt made good — noticeably better than the 5.0 kt of sailing dead downwind at 180°. That gap is exactly why real racing (and this game) rewards zig-zagging upwind and reaching-and-jibing downwind rather than pointing straight at the mark.

At runtime the server needs speed at arbitrary angles and wind strengths, not just these twelve sampled rows, so PolarTable.Evaluate does a bilinear interpolation: linear between the two nearest TWA rows, linear again between the two nearest TWS columns. That's cheap enough to run per boat per tick and smooth enough that players never feel a seam between table entries. 40° — the table's lowest sampled angle, and this chart's own close-hauled label — is also this boat's no-go boundary (noGoHalfAngleDeg).

Why a lookup table instead of simulated lift & drag

A physically simulated sail computes lift and drag from apparent wind angle and a sail's aspect ratio, which is how higher-fidelity sailing sims do it. It's more "real," but the coefficients are non-trivial to tune, the output is harder to keep server-cheap at 20+ boats, and — most importantly for a competitive game — it's harder to guarantee two clients converge on the exact same number after a lossy network hop. A table lookup is fast, deterministic, and easy for a designer to reshape by editing numbers instead of aerofoil coefficients.

Inside the no-go zone: ease down, cross zero, drift — don't clamp

The table has nothing to say below 40° TWA — real polar data doesn't try to describe a boat pointed into the no-go zone, because there's no steady-state speed to measure there. For the game we can't leave it undefined, so we replace it with a purpose-built curve: from 40° inward, speed doesn't hold the table's edge value or jump to zero, it eases smoothly toward zero using a smoothstep blend (zero derivative at the 40° join, so there's no seam against the table), crosses zero somewhere short of dead upwind, and at true 0° settles into slow backward sternway — the boat drifting stern-first at a fraction of true wind speed, same as a real dinghy with sails luffing and no rudder authority to speak of.

noGoSpeed(absTwaDeg, twsKnots) — the 0–40° blend
TermDefinition
fullCloseHauledPolarTable.Evaluate(40, tws) — matches the table exactly at the join
drift−tws × sternwayDriftFactor (default 0.06, i.e. ~6% of true wind speed, backward)
easedsmoothstep(absTwa / 40) — 0 at dead upwind, 1 at the 40° boundary
resultlerp(drift, fullCloseHauled, eased)

Trim still matters here, but asymmetrically: it scales the forward-drive portion of that blend (there's a real sweet spot to chase while pinching), but it doesn't touch the backward drift — sail trim doesn't meaningfully change how fast the wind pushes a stalled hull backward, so a badly-trimmed boat in irons drifts the same as a well-trimmed one.

04 · Design decision

What the model deliberately leaves out

Full velocity-prediction-program (VPP) sailing physics also model heel angle, hull drag as a function of displacement and wetted surface, leeway, and separate lift/drag coefficients that change shape with apparent wind. None of that is simulated here — heel is a cosmetic tilt driven by TWA and speed for visual feedback only, and it never feeds back into the speed calculation. That's a conscious trade: this is an arcade racer for a phone, not a VPP, and every one of those systems adds tuning surface area without adding much to how the game actually plays or reads on a 6-inch screen.

What the table-driven model does preserve, because it's what actually creates the tactical decisions that make sailing races interesting: the no-go zone forcing upwind tacking, the speed curve rewarding wide reaching angles, and the real cost (below) of changing tack.

05 · Maneuvers

Tacking & gybing

A boat's tack is simply which side the wind is hitting first — port tack if TWA is measured to the left of the bow, starboard if to the right. Tacking is crossing through the no-go zone to switch tacks while sailing upwind; gybing is the downwind equivalent, turning the stern through the wind at TWA near 180°.

Two rules keep this from being an exploit rather than a maneuver:

  • Momentum loss through the zone. While absTwa < noGoHalfAngle, target speed follows the noGoSpeed blend rather than the outer polar curve — it eases down, crosses zero, and can even go slightly negative if a tack is slow, with current speed chasing that target at the normal acceleration rate. A clean, fast tack barely dips below the close-hauled speed on either side; a slow one visibly costs way, exactly like real sailing.
  • Tack lockout. After a completed tack or gybe, a short cooldown (see tuning knobs) blocks another tack. Without this, rapid heading oscillation right at the zone boundary could be used to fish for a favorable polar lookup on every tick; the lockout removes the incentive without needing to detect the pattern explicitly.

Right-of-way is covered separately below, now that a first version of it is implemented rather than deferred.

06 · Racing rules

Right-of-way & penalty turns

Real fleet racing runs on the Racing Rules of Sailing (RRS), a dense rulebook covering dozens of situations. The prototype implements a deliberately small slice of it — the two rules that actually come up constantly in a two-boat windward-leeward race — rather than attempting the full rulebook:

  • RRS 10 — opposite tacks. When one boat is on port and the other on starboard, port must keep clear.
  • RRS 11 — same tack. When both boats are on the same tack, the windward boat must keep clear of the leeward boat. "Windward" here is decided by projecting both boats' positions onto the downwind axis (the line the wind is blowing along) and comparing which sits further upwind on it — that's a stand-in for the true geometric test (which boat's line would cross the other's transom) and is accurate for the common case but not for extreme angles-of-approach edge cases.

A foul is detected the same way for both boats — there's no special-casing the player vs. the AI — whenever the two hulls close to within infringementRadiusM of each other during the racing phase, whichever boat the rule above says is give-way gets penalized, unless it's still within its post-penalty immunity window (see below) or a penalty is already in progress for either boat, which keeps the system to one foul at a time rather than a cascade.

The penalty: a real 360° turn, not a timer

Rather than docking time or freezing the boat — either of which would feel like an arbitrary punishment bolted on top of the physics — the penalty is the same thing real sailors do to exonerate a foul: a complete 360° turn, sailed through the model's actual physics. The moment a penalty starts, the boat's target heading is pinned 45° ahead of its current heading every tick, which keeps forcing a turn (through the no-go zone and all) until accumulated heading change reaches penaltyTurnDeg. That means the turn costs exactly what it should: a boat caught head-to-wind mid-turn genuinely slows and can drift backward, same as it would sailing that heading change on purpose, and a boat in open water on a fast reach loses less. Once the turn completes, control returns to the player (or the AI's own autopilot) immediately, and a short penaltyImmunitySec grace period prevents the same proximity from re-triggering the penalty before both boats have actually separated.

What this leaves out, deliberately: mark-room rules (RRS 18), tactical rules around the start line (RRS 14–17), and any rule requiring predicting a future collision course rather than reacting to present proximity. All of those add real tactical depth but need either a bigger rulebook or a geometric closing-speed model this doc doesn't yet specify — reasonable follow-ups once the two-boat case is proven out.

07 · Input mapping

Touch controls — what physics needs from input

This doc isn't the touch-control design (that's next), but the physics model constrains it in two concrete ways worth settling now, since the networking layer needs to know the shape of the input it's carrying.

Heading

The client never sends a raw heading value — it sends a target heading, and the server turns the boat toward it at a bounded rate (turnRateDegPerSec, itself slower right at the no-go zone boundary to reflect a stalling boat's sluggish rudder authority). This keeps a laggy or malicious client from teleporting its heading, and it's also just a better feel: a compass ribbon the player drags, or a virtual joystick that sets a target rather than a rotation delta, both map naturally onto "target heading" as the wire value.

Sail trim

Trim is modeled as a single scalar, trimEfficiency01 (0–1), multiplied against the polar-table speed. Two ways to let the player produce that number, not mutually exclusive:

  • Auto-trim (assist / default): efficiency is pinned near 1.0 automatically — the game trims for you, and skill expression comes entirely from heading and tactics. Good default for a mobile audience that didn't come here to learn sail theory.
  • Manual trim (skill layer): the player drags a trim slider toward an unmarked "sweet spot" that shifts with TWA; efficiency falls off the further they are from it. Rewards players who learn the wind, without requiring them to.

Manual trim efficiency, simplified

efficiency01 = 1 − clamp(|trimAngle − idealTrimAngle(twa)| / maxTrimError, 0, 1) ^ 1.5 — the exponent just makes the sweet spot forgiving near the center and punishing at the extremes, so small misjudgments barely cost anything but ignoring trim entirely does.

08 · Multiplayer contract

Server authority & sync

The full networking design is its own doc, but the physics model exists specifically to make that doc easy to write: everything above runs identically whether it's evaluated for one boat locally or twenty boats on a server, because it's pure functions over small state (heading, trim, tack, position) plus one shared, seeded environment (wind). That's what makes ~15 Hz server-authoritative simulation with client-side interpolation viable on mobile networks without the physics itself becoming the hard part.

This is the full extent of what this doc claims about networking — room/lobby management, reconnection handling, and interpolation-buffer tuning belong in the dedicated networking doc, next up.

09 · Reference

Data structures & server tick

Rough C#-flavored pseudocode, close enough to drop into a Unity server project as a starting point:

// Per-boat state, owned and mutated only on the server
struct BoatState {
    Vector2 position;
    float   headingDeg;
    float   targetHeadingDeg;
    float   speedKnots;
    float   trimEfficiency01;
    int     tackSign;         // -1 port, +1 starboard
    float   tackLockoutTimer;
}

// Resolved once per tick, shared by all boats in the race
struct WindState {
    float directionDeg;
    float speedKnots;
}

// Bilinear lookup over the reference table (rows: 40/45/50/60/75/90/110/120/135/150/165/180deg)
class PolarTable {
    float Evaluate(float absTwaDeg, float twsKnots) {
        var (twaLo, twaHi, tTwa) = BracketAngle(absTwaDeg);
        var (twsLo, twsHi, tTws) = BracketSpeed(twsKnots);
        float a = Lerp(Grid[twaLo][twsLo], Grid[twaLo][twsHi], tTws);
        float b = Lerp(Grid[twaHi][twsLo], Grid[twaHi][twsHi], tTws);
        return Lerp(a, b, tTwa);
    }
}

// Inside the no-go zone: ease to zero, then to a small backward drift.
// Zero derivative at NoGoHalfAngleDeg keeps this seamless against PolarTable.
float NoGoSpeed(float absTwaDeg, float twsKnots) {
    float full  = PolarTable.Evaluate(NoGoHalfAngleDeg, twsKnots);
    float drift = -twsKnots * SternwayDriftFactor;      // default 0.06
    float t     = Mathf.Clamp01(absTwaDeg / NoGoHalfAngleDeg);
    float eased = t * t * (3f - 2f * t);                 // smoothstep
    return Mathf.Lerp(drift, full, eased);
}

// Runs at a fixed 15 Hz on the server; never on the client for scoring
void ServerTick(float dt) {
    WindState wind = WindModel.Evaluate(raceSeed, serverTime);

    foreach (var boat in boats) {
        float twaSigned = WrapAngle(wind.directionDeg - boat.headingDeg);
        float absTwa     = Mathf.Abs(twaSigned);
        bool  pinching   = absTwa < NoGoHalfAngleDeg;

        boat.headingDeg = TurnToward(
            boat.headingDeg, boat.targetHeadingDeg,
            TurnRateDegPerSec(absTwa) * dt);

        float trimPenalty = Mathf.Lerp(0.55f, 1f, boat.trimEfficiency01);
        float targetSpeed;
        if (pinching) {
            float raw = NoGoSpeed(absTwa, wind.speedKnots);
            // trim scales drive, not the wind-driven backward drift
            targetSpeed = raw > 0f ? raw * trimPenalty : raw;
        } else {
            targetSpeed = PolarTable.Evaluate(absTwa, wind.speedKnots) * trimPenalty;
        }

        boat.speedKnots = Mathf.MoveTowards(
            boat.speedKnots, targetSpeed, AccelKnotsPerSec * dt);

        boat.position += HeadingToVector(boat.headingDeg)
                          * KnotsToMetersPerSec(boat.speedKnots) * dt;

        UpdateTackState(boat, twaSigned, dt);
    }

    Broadcast(BuildSnapshot(boats, wind));
}

10 · Balancing

Tuning knobs

Everything here is meant to be exposed to design, not buried in code, so the boat can be balanced without a rebuild:

noGoHalfAngleDeg35–45°, per boat class (40° for the Finn)
sternwayDriftFactor~0.06 × TWS, backward drift when in irons
turnRateDegPerSeccurve vs. TWA, slower near the zone
accelKnotsPerSechow fast speed chases the polar target
tackLockoutSec~1.5–3s, prevents tack-spam
gustAmplitude / gustPeriodseeded wind variance over time
interpolationDelayMsrender-time offset, ~100–150ms
maxTrimErrorforgiveness window for manual trim
polarTable[boatClass]swap per boat if multiple classes ship
infringementRadiusM~5m, proximity that counts as a foul
penaltyTurnDeg360°, matches the real-world penalty turn
penaltyImmunitySec~4s post-penalty grace period

11 · Status

Open questions & next steps

Next docs: networking (room/lobby lifecycle, reconnection, interpolation buffer depth) and touch controls (compass-ribbon vs. joystick heading, trim gesture) both build directly on the contracts defined here — the state this doc treats as fixed (target heading, trim scalar, server snapshot) is what they'll design against.

Unresolved: whether the game ships one boat class or several with distinct polar tables; whether right-of-way ever grows past RRS 10/11 into mark-room and start-line rules; and whether marks/current/tide are ever modeled or stay purely cosmetic. None of these block starting the single-player prototype.

Suggested build order from here, unchanged from the original plan: get this physics model driving a single boat with placeholder touch input, then broadcast raw positions from a dumb server, then swap in the authority model above, then layer race rules and a start sequence on top.
